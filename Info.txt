1.3 Cómo inicia sesión el usuario
La única vía cableada a la UI es OAuth de Discord con polling (no hay formulario email/contraseña en esta versión):

UI: source\ui\pages\src\login.cpp:66 — botón "Continue with Discord" → api.LoginWithDiscord().

Flujo (source\api\api.cpp:449-536), con #define BACKEND_BASE "https://backend-snow-services.crisu.qzz.io" (api.cpp:18):

Genera un state aleatorio de 16 hex (api.cpp:451-459).
Abre el navegador con ShellExecuteA a: GET {BACKEND_BASE}/rmx/server/api/v1/discord/auth?state=<state> (api.cpp:465-466).
En un hilo aparte hace polling cada 2 s, hasta 45 intentos (90 s) a: GET {BACKEND_BASE}/rmx/server/api/v1/discord/pending/<state> (api.cpp:469-476).
Si la respuesta contiene "pending":true sigue; si no, parsea token y user{id, display_name, role_name, role_color, profile_picture} y fija r_auth_token, r_account_id, r_account_name (api.cpp:480-507). Descarga el avatar como bytes y lo sube a textura D3D11.
r_auth_done = true → guarda sesión y arranca bucles de refresco (amigos + jugadores cada 30 s, api.cpp:518-528).

2.4 Manejo de auth (resumen)
Tokens: JWT HS256 firmados con JWTSECRET (env), sesiones persistidas en el bucket Accounts_Sessions con TTL 24 h (ticker de limpieza, main.go:746-779). El middleware ClientAuthMiddleware (utilities\middleware\auth_client.go:31+) valida el Authorization: Bearer buscando el token en Accounts_Sessions, con caché en memoria de 30 s y rechazo de cuentas baneadas.
Exchange codes: bucket ExchangeCodes con validez de 5 minutos (oauth_create.go:110-115).
Device auth: POST /account/api/public/account/:accountId/deviceAuth y v3.
Discord OAuth: state temporal en pendingAuthMap (TTL 10 min, limpieza cada 5 min) + bot token para leer roles del guild (roles también usados como gate beta y para colorear el rol en el launcher).
Arc (externo): el backend puede desactivar el anticheat Arc de una cuenta llamando a dev-anticheat-v1.arc-services.dev con X-Arc-Auth fijo y X-Arc-Client: zszxfhpnjgzxzvpiiopxqrfpivjqhxbh (remix_server_account_management.go:187-191).
2.5 ¿Cómo funciona sin puerto local del launcher?
Todo es un único servidor HTTP(S) público (dominio backend-snow-services.crisu.qzz.io, escuchando en :4880 y :443 con TLS propio). No existe ningún componente cliente que abra puertos:

El launcher solo habla HTTPS saliente (WinINet) contra ese dominio (login Discord, amigos, contador, update).
En el lanzamiento, el launcher pasa el token de sesión del backend como -AUTH_PASSWORD y el cliente modificado del juego (RemixClient-Win64-Shipping.exe, descargado de r2.ploosh.dev) lleva hardcodeada la URL del backend: hace su POST /account/api/oauth/token (grant password con usuario@project.remix), y todas las llamadas de servicio (MCP, amigos, party, tienda, matchmaking vía WebSocket /xenon/matchmaking/*, XMPP/Synapse para presencia) van directo al dominio público.
El 127.0.0.1:4040 que aparece en el código es solo interno del servidor (mini-HTTP del módulo matchmaking para /connections y /friends/status), no del cliente.
